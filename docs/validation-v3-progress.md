# 本轮进度与可使用的研究结论

工程主体和新的验收入口已完成。当前新增的是“实际 MCP 选工具 → 冻结证据 → 配对 v3 正文条件”流程，
以及新合成抓包、严格生成请求预算、失败留在分母、源字段重提取、离线重算与人工语义标签。
研究尚未结束：本轮没有在用户的 Ollama 上生成新正文，跨模型、外部真实流量和最终研究写作仍待完成。
不据此把上一轮约 80% 的阶段估算改写成新的精确完成率。

## 已有结果与本轮验证的区别

已有 v3 保存结果共 10 次正文请求，本轮重新计算与原汇总一致；结构和引用合法不能证明语义正确。
原有 80 个源码/脚本/测试文件与上传版本字节一致，1887 个旧实验文件与原 ZIP 字节一致。
这些数量是本轮逐文件核对的结果；它们不代表实验样本数。

本轮完整 pytest：282 passed，3 subtests passed，没有跳过 Wireshark 测试。
新增模块通过 Ruff 和 mypy；wheel 构建、增量安装与边界校验情况见交付包的 verification 记录。
全量 Ruff 仍有两处上传版本已有的 E501（lineage.py 和 test_output_provenance.py），本轮保留冻结文件。
Windows 启动脚本经过 PowerShell 语法树解析；没有在 Windows 主机实际执行，保留该验证边界。

8 个新合成用例经真实 Wireshark 4.2.2 解析，有限 oracle 8/8 匹配，源记录重提取 37/37 匹配。
独立证据在 `baseline-runs/validation-v3-offline-proof-20261011`；这部分生成模型请求数为零。
MCP 集成测试的模型响应来自测试桩，只用于核对控制流、请求配对、预算和重算。
不能把测试桩的正确 JSON 或上述字段结果写成“新模型正文准确率”。

## 接下来怎样推进

先在原目录运行默认两个案例的小批，上限 8 次生成请求，把结果 ZIP 返回。
检查模型是否选到 HTTP 工具、是否仍混淆本地分析程序与远端服务器、是否按有效计数表述、
是否把存在性/启发式警告误写成意图或攻击成功，再决定是否开 8 案例或第二个模型。
失败不补跑到成功；如果确实要修改提示词或修复实现，重新命名协议阶段和结果目录。

真实流量阶段需要自有抓包和独立标注。没有标注时，源重提取仅证明导出记录可复核，
不证明调查结论正确，也不证明覆盖整个抓包。评测结论应分开说明工具可用性、闭合事实完整性、
来源一致性、正文格式/引用合规与人工语义结果。

## 面试可以怎样讲

“我做了一个只读的抓包分析 MCP Server 和有预算的 Agent。困难不只是让模型选工具，
而是让它正确理解被分析程序转换过的证据。例如，模型可能把本地程序插入的中点说成网络对端的编码或规避行为。
我因此给每个 HTTP 字段 occurrence 添加抓包哈希、帧号、字段定位、解码与转换计数，
再把有限事实与来源标签交给程序生成，让模型只提出未验证解释和限制。
评测同时保留原始脱敏输出、失败和未尝试结果，并能重新从抓包提取字段来核对。
合法 JSON 和正确引用仍可能包含错误解释，所以语义需要单独审阅。”

被追问效果时，先讲清各实验的证据来源和限制，再报告对应结果。
目前可以证明确定性事实生成与重提取链路，不能宣称已普遍消除语义错误或成功防御所有提示注入。
